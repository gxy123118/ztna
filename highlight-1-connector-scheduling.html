① 问题背景：两个「随机」造成的核心矛盾

网关是 K8s 多实例 + 多区域（张家口 zjk / 深圳 sz / 杭州 hz）部署。连通器部署在企业内网， 主动出站反向拨号连接网关（企业防火墙零入站端口，这是 ZTNA 区别于 VPN 的根本），但：

  • 连通器拨号时，SLB 随机把这条长连接分到某个网关 Pod A；
  • 用户请求进来时，SLB 又随机把请求分到 Pod B。
核心矛盾 「请求所在实例 ≠ 连通器所在实例」是常态。怎么把 B 上的请求送进 A 上的隧道？ —— 这与微信/钉钉 IM 网关「消息如何找到用户连的那台接入机」是同构问题。

为什么应用要配多个连通器 / 连通器组？三个业务动机：

  • 高可用：单台连通器挂了，候选集里的其他实例自动接管；
  • 水平扩容：流量大时加实例分摊（连接数加权随机）；
  • 运维单元化：连通器组作为复用单元，一组连通器服务一批应用。

③ 域名接入：两种域名，两种解析方式，一种证书架构

关键前提 网关 Pod 的用户面服务是纯 HTTP 监听（web/ztna/router.go → router.Run(":port")，无 TLS/SNI 代码） —— 所有 HTTPS 在阿里云 SLB/ALB 上终止，网关进程只看明文 HTTP 的 Host 头。这决定了自定义域名为什么要「上传证书」。

A. 自动生成域名（平台子域名）

  • 创建应用时自动拼出 {名称}-{uuid}.gw.ztna-dingtalk.com，映射写入 application_uri 表（GwUri ↔ CorpUri）；
  • 基础设施提前一次就绪：DNS 泛解析 *.gw域名 → SLB + SLB 挂平台泛域名证书， 新应用即刻可用、零 DNS/证书操作；
  • 自描述域名：解析时去掉网关域名后缀、取最后一个 - 或 . 之后的段即 app uuid —— 「域名→应用」这个每请求必做的高频操作零查库 （urlutils.go GetUuid()）。
oa-4f7a9b2c.gw.ztna-dingtalk.com
   └──────┘ └──────────────────┘
    uuid      网关域名后缀(配置 Gateway.Domains)
→ 字符串切割直接得到 uuid=4f7a9b2c，不查任何表

B. 自定义域名（客户自有域名，需上传证书）

  1. 为什么必须上传证书：TLS 握手要求服务端出示与访问域名匹配的证书；平台只有 *.ztna-dingtalk.com 泛证书，客户域名的证书只有客户能申请；
  2. Console 侧（Java，本人负责模块）：证书+私钥落库 → AliyunCertificateManager.uploadCertificate() 上传阿里云 → bindCertificate(regionId, albListenerId, certId) 绑到 ALB 监听； ALB 单监听挂 N 张证书，握手时按 SNI 自动选取；
  3. 应用配置自有域名 → application.self_domains(JSON) + application_uri 新增映射行；
  4. 客户在自己 DNS 服务商配 CNAME 指向网关接入地址；
  5. 网关解析：IsSelfDomain=true（不匹配平台域名后缀）→ uuid 切不出来 → 查表 ListByGwUri(url) 反查 uuid （applicationv2service.go getUuidBySelfDomain）。
对比项自动域名自定义域名
配置成本零（泛解析+泛证书提前就绪）上传证书 + 绑 ALB + 客户配 CNAME
域名→应用解析字符串切割 uuid，零查库查 application_uri 表
TLS 证书平台泛域名证书客户证书，ALB 按 SNI 选
业务价值开箱即用品牌域名、Cookie 域独立
复用设计：一份配置驱动两个引擎 application_uri 的同一行数据：正向（Gw2Corp）作为隧道内的转发目标； 反向（Corp2Gw）驱动响应内容的链接翻译（把页面里写死的内网地址翻译回网关域名），实现存量系统零改造接入。

④ 阶段 1：连通器上线注册（深度）

连通器部署在企业内网服务器，主动出站连接网关公网接入地址 （agent.ztna-dingtalk.com），TCP+TLS 与 QUIC 双协议监听同一端口。

4.1 身份认证：传输层 TLS + 应用层 AK/SK 两层

第一层：TLS 单向认证（连通器验网关）

网关出示 ZTNA 自建根 CA（有效期 2023-2033）签发的服务端证书，连通器内置根 CA 公钥校验「连的确实是钉钉网关」，防中间人。

纠错记录 连通器接入不是双向 mTLS（代码 certificate.go Set[Connector].MTls=false）； 双向 mTLS 只用于网关 Pod 之间的 Relay 互连（Set[Relay].MTls=true）。连通器数量大且部署在客户环境，发客户端证书运维成本高，身份靠第二层。

第二层：AK/SK 五步校验（网关验连通器）

  1. 用 AK 查 connector 表，查不到拒绝；
  2. 查所属租户，企业未注册拒绝；
  3. 租户状态校验：试用版过期拒绝接入（商业化控制点做在认证链路里）；
  4. SK 校验：库中不存明文，存 DES-ECB(SK, key=租户Code) 密文，上报值同算法加密后比对；
  5. identityCode 实例校验：不存在→首次上线自动创建实例（自动发现）；存在→校验租户归属一致（防跨租户冒用）+ 未删除。

失败时把错误写回连通器再断连，便于客户侧排查。connectorservice.go IdentifyConnector

4.3 Pod IP 怎么获取（关键细节）

ztnaIp := strings.Split(c.NetConn().LocalAddr().String(), ":")[0]   // auth.go register()

就是这条 TCP 连接的本端（网关侧）地址。socket 天然知道两端 IP： LocalAddr() = 本 Pod IP（写入 ZtnaIp，跨 Pod 寻址用）； RemoteAddr() = 连通器公网出口 IP（写入 PublicIp，运维排查用）。 不读环境变量、不调 K8s API。

4.4 双写注册：数据面与控制面的分离

4.4.0 零基础前置：内存路由表到底是什么？

第一性原理：程序里的「一条 TCP 连接」是一个对象 Java 里的 Socket / Go 里的 net.Conn = 一个「活的听筒」： 对它 Write() 字节就真的从网卡发出、到达对端。它有两个致命特性： ① 只存在于接住它的那个进程的内存里（文件描述符是进程内编号）； ② 无法序列化存 DB（存进去的只能是描述文字，不是能写字节的听筒本身）。 这就是必须双写的根源：DB 存「听筒在哪」，听筒本身只能留在那个 Pod 手里。

一个 Pod 同时接着成百上千条连通器连接。选路决定「发给 conn-prod-01」后，Pod 面临的问题是： 手里几千个听筒，哪一个才是通往 conn-prod-01 的？内存路由表就是回答这个问题的查找索引， Java 完全等价物是 IM 服务器的 ConcurrentHashMap<String userId, Channel>： 给张三推消息 = onlineUsers.get("zhangsan").writeAndFlush(msg)。

一次转发的四步代码链（它被怎么用）

① 查表拿对象   conns := identity2conn["conn-prod-01"]; conn := conns[1]
              → 拿到 ZConnector 对象（包着当初 accept 的 TLS socket）
              → 放入请求上下文 ctx.Keys[CtxKeyLocalConnector]        // connection_manager.go GetConn
② 处理器调用   connectorConnection.HttpRequest(ctx, ...)              // http_gatewayserver_handler.go L126
              → 这个对象不只是数据，它是「能干活的听筒」（Connector 接口有 HttpRequest 方法）
③ 开流写入     stream := c.Connection.NewStream(streamId, meta, ...)   // zconnector.go L154
              → 把用户 HTTP 请求字节写进 stream，底层就是对那个 socket 的 Write()
④ 字节到达     顺着连通器当初主动出站建的那条物理连接（穿过防火墙）到达企业内网，
              连通器按 streamId 拆出请求转发给 oa.internal:8080

关于「流」只需一句话：一条 TCP 连接同时跑很多个用户请求，每段数据贴 streamId 标签区分——像一条高速公路上不同车牌的车（类似 HTTP/2 stream 思想）。

内存路由表DB 位置表
存什么identity2conn[identityCode][subId] = conn（活的连接对象：socket、缓冲区、goroutine） ZtnaIp + Region + PublicIp/PrivateIp + Version + 在线状态
可见范围仅接入 Pod 进程内（物理上不可能放 DB/Redis，类比 Netty Channel 无法序列化） 全集群可见
服务于数据面：本 Pod 转发流量直接取连接开流 控制面：跨 Pod 选路寻址、Console 在线状态展示、心跳租约载体
总机类比（一句话记住两张表） DB 位置表 = 全公司共享的登记簿（「张三的电话接在 3 号楼 B 前台」，回答去哪个 Pod）； 内存路由表 = B 前台桌上实际插着的那排电话线（每条线贴名字标签，回答拿起哪个听筒真正写字节）。 relay 转发的本质：按登记簿找到 B 前台、把话务转接过去，由 B 前台拿起正确的听筒说话。 双写不是冗余，是数据面/控制面分离。

4.5 多连接支持（supportMulti / subId）

业务问题：一个 identityCode 只有一条隧道连接就是单点，吞吐也被单连接限制。 允许同一 identityCode 由多进程/多台内网服务器同时在线，每条连接用 subId 区分。

  • subId 分配（DB 全局协调，两条连接可能落在不同 Pod）： 先复用「离线或租约过期（60 秒无心跳）」的坑位 → 无可复用则 max(sub_id)+1 插新行 （connector_instance_multi_mapper.go SubIdForMulti）；避免 subId 无限增长；
  • 内存表按 [identityCode][subId] 二级索引；同 Pod 重复注册在 SetConn 冲突拒绝；
  • Leader 干活：多连接在线时，仅同 Region 最小 subId 的连接负责刷新公共状态（legacy 状态/Region）， 避免 N 条连接重复写同一行 DB（zconnector.go Modified()）。

4.6 subId 专题：多服务器同Pod 的三种情况

一句话定义 subId = 同一个连通器身份下，第几条物理连接的编号。 内存路由表的 key 是 [identityCode][subId]—— 第一级定位「哪个身份」，第二级定位「这个身份的第几条连接」。特殊值 subId=0 是单连接模式（老版本/不支持 multi）的约定值。

分配 SQL 里 where 条件只有 id=连通器身份，没有 Pod 信息—— subId 是逻辑编号，由 DB 按身份全局协调；Pod 是物理落点，由 SLB 随机决定；两者解耦。 DB 表 connector_instance_multi 每行 (id, sub_id) 还带 ztna_ip 字段记录落点，编号与位置是同一行里的两个独立字段。

情况一：多服务器用【相同】连通器，拨到【同一个】Pod

服务器A(conn-prod-01) → Pod .2 → 分配 subId
   ①无空闲坑位 ②max空→0 ③新编号=1
   内存表：["conn-prod-01"][1] = A的连接

服务器B(conn-prod-01) → 同 Pod .2 → 分配 subId
   ①subId=1 在线，不算空闲 ②max=1 ③新编号=2
   内存表：["conn-prod-01"][2] = B的连接
→ 同 Pod 内存表里 conn-prod-01 下挂了 [1] 和 [2]，互不冲突；
   选路时都算「同实例」候选，加权随机二选一

情况二：【不同】连通器，拨到【同一个】Pod

conn-prod-01 → Pod .2 → 分配 subId=1 （在 prod-01 自己的编号空间）
conn-prod-02 → Pod .2 → 分配 subId=1 （在 prod-02 自己的编号空间，也是1）

内存表（两级 key，各占各的格子）：
  ["conn-prod-01"][1] = prod-01的连接
  ["conn-prod-02"][1] = prod-02的连接
→ subId 都等于 1，但完全不冲突——印证了 subId 只在「身份内部」唯一，不是全局唯一

情况三：混合 Pod 的内存表长什么样

Pod .2 的 identity2conn 实际形态：
  ["conn-prod-01"][1] = 服务器A        ["conn-prod-01"][2] = 服务器B   ← 同身份，靠subId区分
  ["conn-prod-02"][1] = 服务器C                                          ← 不同身份，subId重新从1算
  ["conn-finance"][1] = 服务器D
  ...（成百上千个身份 × 各自若干条连接）
并发分配的兜底与改进点 情况一里 A、B 同时拨到同 Pod，可能都查到 max=1、都想拿 subId=2。 同 Pod 内：第二个执行 SetConn 时发现格子已被占 → 返回冲突 → 注册失败回滚（auth.go register() SetConn 失败回滚），连通器重连即可恢复； 跨 Pod：两个 Pod 的内存表互相看不见，这层兜底失效。改进方案：给 (id, sub_id) 加唯一索引，insert 冲突重试。

⑤ 阶段 2：心跳租约与僵尸剔除（Lease 模式）

5.1 业务背景：DB 位置表天生是「历史记录」，不是「实时事实」

所有 Pod 靠位置表回答「conn-prod-01 在哪、活着吗」，但那行「在线@33.1.1.2」只是某时刻写下的历史。下线分两种：

  • 可感知下线：TCP 断开但 Pod 进程活着 → 读 socket 报错 → 执行 Unregister → DB 标离线，闭环干净；
  • 不可感知下线（真正难题）：Pod 自己整个死了（OOM 被杀/宿主机宕机/断电），没机会执行任何清理代码， DB 里的「在线」记录成了谎言 —— 僵尸记录。危害：选路选中它 → relay 转发到死 Pod → 请求失败，且无人清理会永远错下去。

5.2 方案选择：为什么用租约

方案做法代价
中心化健康检查单起探活服务轮询所有 Pod多一个组件，它自己也会挂
分布式协调组件etcd/ZooKeeper 临时节点，会话断自动删引入重依赖
租约 Lease（本项目）记录自带保质期：写方定期续期，读方过期不认零新增组件，一个时间戳字段搞定
保质期类比 DB 记录是罐头，gmt_modified 是生产日期，60 秒是保质期。 工厂（Pod）活着就不断生产新日期的罐头（刷时间戳）；超市（读取方）上架前看日期，过期直接下架销毁。 工厂猝死了？它生产不出新罐头，旧罐头 60 秒后自动失效——不需要打电话问「你还活着吗」。

代码① 心跳触发：连通器发 Ping，连接层回调业务

代码② 续约：Modified → 一条 UPDATE 刷新时间戳

// connector_instance_mapper.go L157-159：续约的本质就是这条 SQL
update connector_instance set gmt_modified = now()
where identity_code='conn-prod-01' and ztna_ip='33.1.1.2'      -- 只续自己Pod名下的记录
  and (conn_status=在线 or conn_status=优雅下线中)              -- 已判死的不允许靠迟到心跳「诈尸」

代码③ 判死：读取方加载候选集时看保质期（惰性）

// connector_cache_manager.go L151-156
if time.Now().After(GmtModified.Add(time.Minute)) {   // 超过60秒没续约 → 僵尸
    UpdateConnStatus(..., Disconnected, ...)           // 主动回写离线，顺手销毁
} else {
    validIdentityCodes = append(...)                   // 保质期内 → 进候选集
}

判死是惰性的：没有定时任务扫表，而是「谁来读、谁顺手检查、谁负责销毁」，成本摊薄到每次读取，零额外调度。

5.4 完整例子：Pod 被 OOM 强杀的时间轴

10:00:00  subId=1 心跳 → gmt_modified = 10:00:00
10:00:05  心跳 → gmt_modified = 10:00:05   （每隔几秒续约，记录始终新鲜）
10:00:30  最后一次续约，gmt_modified = 10:00:30

10:00:31  ★ Pod .2 被 OOM kill，进程瞬间消失（没执行 Unregister）
          DB 里 subId=1 仍显示「在线@33.1.1.2」—— 僵尸诞生

10:00:31~10:01:30  僵尸窗口期（最长≈60秒租约 + 5秒候选集缓存）
          选路仍可能选中 subId=1 → relay 到死Pod → 部分请求失败
          （加权随机下也可能选到 subId=2 成功）

10:01:31  某请求触发候选集重新加载：61s > 60s → 判死！
          不进候选集 + 回写 Disconnected —— 僵尸被销毁

之后      候选集只剩 subId=2，流量 100% 走 Pod .3，用户无感知
          （多连通器配置的价值兑现时刻）
内网侧    连通器客户端发现连接死了 → 自动重连 → SLB 分到健康 Pod
          → 重新注册（复用已离线的 subId=1 坑位）→ 恢复双连接

5.5 两层「心跳」各管一件事（易混点）

连接层心跳（Ping/Pong 超时）DB 租约（gmt_modified）
保什么「这条 TCP 连接活着」「这条 DB 记录可信」
谁检查连接两端自己（超时就关连接）任何读位置表的 Pod
兜什么底网络假死/对端无响应 → 关连接触发 Unregister进程整个猝死、连清理代码都没跑的场景
一句话（面试用语） 连接层心跳管「活连接」，处理可感知的死亡；DB 租约管「真记录」，兜底不可感知的死亡。 写路径心跳续约 + 读路径过期判死，不依赖任何中心化健康检查组件。

配套缓存设计：连通器候选集缓存 TTL 仅 5 秒（应用配置缓存 60 秒）—— 在线状态变化远快于应用配置，不同数据不同 TTL。

⑥ 阶段 3/4：三级就近选路与 Relay 转发

6.1 三级就近选路（Locality-Aware Routing）

候选连通器按物理距离分三档，严格就近优先（SelectConnectorCode）:
1. 同实例(sameMachine): 连通器连在本 Pod → 直接进隧道，零转发
2. 同区域(sameRegion) : 连通器在本 Region 其他 Pod → 区域内 relay 一跳
3. 跨区域(all)        : 其他 Region → 跨区域 relay（{region}-relay.ztna 域名）

同档内按连接数加权随机: StringIntPair{code, 连接数} 加权抽取
—— 连接多 = 容量大 = 分到流量按比例更多（负载均衡不是简单随机）

6.2 Relay 转发通道：懒加载连接池 + 双重检查

业务问题

请求到了 Pod B，连通器在 Pod A，需要建一条到 A 的连接把请求送过去。 每个请求都现建连接 → 建连耗时（TCP 握手+TLS）高并发下延迟爆炸； 启动时全建好 → 浪费（很多 Pod 用不到）且 Pod 动态扩缩容建不全。

解法：懒加载 + 池化 + 双重检查

  • 懒加载：第一次需要转发到某 Pod 时才建连接，之后复用；
  • 池化：建一个连接池（MinPool=5, MaxPool=10），多条连接并发承载，避免单条瓶颈；
  • 双重检查：解决"100 个 goroutine 同时发现没连接、同时去建"的浪费问题。
// connection_manager.go getRelayConnection()

// ①加锁查缓存
m.lockRelayConnections.Lock()
conn := m.relayConnections[address]      // 到 Pod A 的池建了没？
if conn != nil { unlock; return conn }   // 建了 → 直接用
m.lockRelayConnections.Unlock()          // 没建 → 释放锁（关键！不持锁做耗时IO）

// ②不持锁，建连接池（耗时：TCP握手，几百毫秒）
vc := ztnaconn.NewVirtualConnection(addrs, {MinPool:5, MaxPool:10})

// ③建完再加锁检查一次
m.lockRelayConnections.Lock()
conn = m.relayConnections[address]       // 我建池期间别人建好了吗？
if conn != nil {
    vc.Close()                           // 别人已建 → 关掉我白建的
    return conn.Connection()
} else {
    m.relayConnections[address] = vc     // 确实没人建 → 我的入缓存
    return vc.Connection()
}
为什么不全程持锁？ 建连接是几百毫秒 IO，持锁期间所有其他地址的转发都被阻塞。 所以「查」持锁（微秒级）、「建」不持锁（几百毫秒）、「再查」持锁——锁只保护 map 读写，不保护耗时 IO。 Java 对照：ConcurrentHashMap.computeIfAbsent 的思路，但 Go 这里手动优化了"不持锁做耗时操作"。

6.3 转发防环：单跳限制

业务问题

极端场景（位置表不一致时）：
  Pod A 收到请求 → 位置表说"在 Pod B" → relay 到 B
  Pod B 收到请求 → 位置表说"在 Pod A" → relay 回 A
  → 无限循环！请求弹皮球，永远到不了连通器，白白消耗资源

解法：FromRelay 标记 + 禁止二次转发

// connection_manager.go SelectConnector()
disallowCrossSameRegion := ctx.Keys[CtxKeyFromRelay].(bool) && !FromOtherRegion(ctx)
// 如果这个请求本身就是 relay 来的 → 禁止再次 relay → 只能本地找或 502
  • 原始请求（用户直接进来）：FromRelay=false → 允许 relay 一次；
  • 被 relay 转发来的：FromRelay=true → 禁止再次 relay，本地内存表找不到就 502 快速失败；
  • 链路硬上限：入口 Pod → 目标 Pod，两跳封顶，不存在 A→B→C 三跳。
设计哲学 宁可让个别请求快速失败（502），也绝不允许环路消耗集群资源。 Fail fast 优于 infinite loop——用户刷新重试即可（此时位置表已更新）。

6.4 会话亲和（有状态应用）

业务问题

有些内网应用是有状态的：文件分片上传（片 1 在 A、片 2 到 B → 合并失败）、 WebSocket 长连接（建连在 A、后续消息路由到 B → 断连）、本地 Session 老系统。 要求：同一用户/会话的所有请求必须打到同一个连通器实例。

解法：JWT 承载 connectorCode

第一次请求（无绑定）：
  认证通过 → 加权随机选中 subId=1 → 把 connectorCode 写进 JWT Claims → 签发 JWT

后续请求（有绑定）：
  浏览器带 JWT → 解析 Claims.ConnectorCode
  → SelectConnectorByCode() → 直达那个特定连通器（跳过加权随机）

绑定失效（目标连通器挂了）：
  SelectConnectorByCode 失败 → 重新选路 → 触发重新认证 → 签发新 JWT（新 code）
  → 该用户会话丢失需重试，但服务恢复（影响面=单个用户）

为什么不用一致性哈希？

方案故障影响面语义
一致性哈希（按 userId）连通器上下线 → 哈希环变动 → 一批用户被重映射近似亲和，不精确
显式绑定（JWT 承载 code）只有绑定的那个连通器挂了才影响那一个用户精确绑定，精确失效
三者协同（一次请求的完整决策链） 请求到达 → 会话亲和：JWT 有 code？有 → 直达（跳过随机）→ 没有 → 三级就近 + 加权随机选出目标 → 目标在本 Pod？是 → 内存表拿连接 → 不在 → relay 连接池取连接转发 → 目标 Pod 收到（FromRelay=true）→ 防环：禁止再 relay → 本地内存表找连接。

6.5 基础设施补充：SLB 后端挂载与三类流量路径

SLB 要挂网关实例，但不是手动挂，而且不是所有流量都走 SLB：

流量类型入口后端挂载/寻址方式走不走 SLB
用户 HTTPS 请求SLB/ALB（TLS 终止） K8s LoadBalancer Service，Cloud Controller Manager 自动同步网关实例（Pod/Node 上下线自动注册/摘除）走
连通器拨号SLB（TCP 透传到连通器端口）同上走
同 Region relay无 位置表里的 Pod IP 直连（tcp://{ZtnaIp}:relayPort）。relay 的目的是「精确到达那一个 Pod」，负载均衡器在此反作用；依赖 VPC 网络插件下 Pod IP 直接可路由不走
跨 Region relay{region}-relay.ztna 内部域名 Diamond 配置中心下发地址表 + 客户端随机负载均衡（connect() 先查 DnsConfig[domain] 替换 IP），不依赖公网 DNS不走公网 SLB
发布平滑下线（面试好料） SLB annotation connection-drain: on / drain-timeout: 60（README）——Pod 下线前 SLB 停止分发新连接并给存量连接 60 秒排空期， 配合代码里的 GraceOffline（网关主动通知连通器优雅迁移重连），实现发布不断连。
不确定项 Diamond 地址表里配的是对端 Region 内部 SLB 还是网关实例 IP，代码不可证，讲之前需核对部署配置；「配置中心做内部服务发现」机制本身代码可证 （cmd/start.go InitDNSConfigFromDiamond · tcpconnection.go connect()）。

⑥⁺ 连接模型基础课（零基础，三个心智模型）

模型一：两张表协作的「三情况转发路径」

关键精确化 内存路由表的查找不是由入口 Pod「远程去查」的——每个 Pod 只查自己的。 入口 Pod 永远读不到别的 Pod 的内存，它只是把请求 relay 过去，由目标 Pod 在自己的内存表里找连接。
情况1：连通器就连在本 Pod（最快路径）
  请求进来 → 查自己的内存表 → 命中！直接拿连接开流收发（位置表/relay 不参与）

情况2：连通器在同 Region 其他 Pod
  查自己的内存表 → 没有 → 查位置表: conn-prod-01 在 33.1.1.2
  → relay 转发到 33.1.1.2 → 33.1.1.2 查【它自己的】内存表 → 命中 → 开流收发

情况3：连通器在其他 Region
  同情况2，只是 relay 目标换成 {region}-relay.ztna，最终仍由
  连通器所在的那个 Pod 查自己的内存表拿连接
面试防露怯 如果说成「根据位置表和内存表找到连接」，面试官会追问「你怎么读到别的机器的内存？」。 正确表述：位置表决定「请求该流向哪个 Pod」（跨进程可见），内存表决定「本进程内拿哪个连接对象」（进程私有），中间靠 relay 把请求物理地送过去。

模型二：单条连接的四层对象封装（纵向嵌套）

一个网关进程同时握着四类连接：连通器隧道连接（成百上千条，存内存路由表）、用户 HTTP 连接（框架管）、 relay 连接（每目标 5~10 条池化）、DB/Redis 连接池。单机几万条连接对 OS 很平常（每条 = 一个文件描述符 + 缓冲区）。

其中一条连通器连接从裸 socket 到内存表里的对象，套了四层，每层加一种能力：

第1层  net.Conn（裸TCP socket）      ← l.Accept() 返回        能力：Write/Read 字节
第2层  tls.Conn（TLS加密层）         ← tls.Listen             能力：字节自动加解密
第3层  tcpConnection（隧道层）       ← NewServerConnection    能力：多路复用/心跳/写合并/流控
第4层  ZConnector（业务层）          ← 认证注册时创建         能力：业务身份/HttpRequest()方法

内存路由表存的是第4层；调用时反着穿回去：
ZConnector.HttpRequest() → Connection.NewStream() → 加密 → socket 发出

Java 对照：Socket → SSLSocket → Netty Channel(pipeline加编解码/心跳) → 业务 UserSession 对象。 另注意对应关系：一条 TCP 连接 = 一个 ZConnector = 一个 subId；但一个连通器身份(identityCode)可有多条连接（supportMulti），所以内存表是两级 key [identityCode][subId]。

模型三：一次请求的五段连接接力（横向）

术语校准 「嵌套」发生在单条连接内部（模型二，纵向）；一次用户请求则是被多段互相独立的连接分段接力传递的（横向）， 网关是「连接之间的搬运工」：读一段、写另一段。
①用户↔SLB     ②SLB↔PodB     ③PodB↔PodA      ④PodA↔连通器      ⑤连通器↔内网应用
   HTTPS          明文HTTP       relay隧道         连通器隧道          普通HTTP
  (TCP+TLS)       (TCP)        (自研协议)         (自研协议)           (TCP)
   短连接          短连接      长连接/池化复用    长连接/常驻            按需建
                              ↑仅内存表未命中时有这段
  • relay 用什么协议：和连通器隧道同一套自研多路复用协议（ztnaconn 的 Connection/Stream 模型通用）； 同 Region tcp://PodIP（VPC 内不加密），跨 Region tls://{region}-relay.ztna（Relay 证书 mTLS，即 Set[Relay].MTls=true 的用处）；
  • 响应不需要重新寻址：stream 双向，请求从哪个 stream 进来，响应就从同一个 stream 写回，每段原路返回；
  • 长短连接分工：②段用户连接是一次性的，④段隧道是常驻高速公路，一条隧道上同时跑着成百上千个用户请求的 stream ——这就是多路复用存在的原因（不可能每个用户请求都让连通器现拨一条穿防火墙的连接）。

⑨ 面试深挖问答清单

可能的追问回答要点
为什么请求和连通器会不在同一实例？ SLB 对两类连接都随机分配，无法感知业务亲和；这是所有「长连接+多实例」系统的固有问题（同 IM 网关）。
怎么知道连通器连在哪个实例？ 上线时接入 Pod 把 (identityCode → 本 Pod IP + Region) 写入 DB 位置注册表；Pod IP 直接取 TCP 连接 LocalAddr()，不依赖 K8s API。
为什么三级就近而不是全局随机？ 同实例零跳、同区域内网一跳、跨区域走专线有延迟/带宽成本；就近省一次实例间转发的序列化+网络开销。
转发环路怎么防？ FromRelay 标记 + disallowCrossRegion，链路硬上限两跳；宁可 502 也不允许环路。
连通器突然挂了怎么办？ 接入 Pod 感知断连 → 实时摘除；Pod 整体被强杀 → 租约 60 秒过期，读取侧惰性判死回写离线；绑定用户自动重选+重新认证；全部不可用 → 502 快速失败。
和一致性哈希方案比较？ 一致性哈希适合无状态分片；这里是「精确找到连通器实际所在实例」的注册表查找问题。会话亲和用显式绑定，避免节点变动时哈希环漂移导致会话漂移。
双重检查那段为什么不全程持锁？ 建连接池是秒级耗时 IO，持锁会阻塞所有其他地址的转发；宁可小概率重复建连再关闭，也不持锁做 IO。
为什么 TLS 终止在 SLB 不在网关？ 证书生命周期收敛到云平台（ALB SNI 多证书 + Console API 管理绑定/解绑），网关进程无状态、不碰私钥；代价是 Pod 内明文，靠 VPC 内网隔离兜底。
两种域名为什么解析方式不一样？ 平台域名可控，把 uuid 编码进域名换取高频路径零查库；客户域名不可控只能查表。性能与灵活性的取舍。
subId 分配有没有并发问题？ 诚实承认：读从库查 max 再插入存在并发窗口，同 Pod 靠 SetConn 注册冲突兜底；改进方案：唯一索引 (id, sub_id) + 冲突重试。
SLB 后端怎么挂载？Pod 上下线怎么同步？ K8s LoadBalancer Service + Cloud Controller Manager 自动注册/摘除，非人工维护；发布时 connection-drain 排空 60 秒 + GraceOffline 通知连通器迁移重连，实现不断连发布。relay 流量不走 SLB：同 Region 用位置表 Pod IP 直连（要精确送达，LB 反作用），跨 Region 用配置中心下发地址表 + 客户端随机。

⑩ 诚实素材：可改进点（被问「有什么不足」时用）

  • subId 分配并发窗口：查 max 再 insert 非原子，应加唯一索引 (id, sub_id) + 冲突重试；
  • SK 加密算法：DES-ECB 属历史选型（弱加密、ECB 模式无 IV），应升级 AES-GCM 或 HMAC 派生比对；
  • Pod 内明文 HTTP：TLS 终止在 SLB 后 VPC 内为明文，零信任语义上可引入 mTLS service mesh 补全；
  • 候选集 5 秒缓存与故障摘除时延：极端情况下故障连通器最长 5 秒 + 租约 60 秒才被完全摘除，可评估事件驱动的主动失效通知。
表述边界（不要说过头） ① 连通器接入是「TLS 单向认证 + AK/SK」，不要说成 mTLS；② 泛解析 DNS 与 ALB 监听拓扑为基于代码与 README 的推断， 对外讲之前建议再核对当时的接入文档；③ 隧道协议层（帧格式/多路复用/流控）不作为本亮点内容，被问到时用一句话带过： 「网关与连通器之间是自研多路复用隧道协议，支持 TCP/QUIC，这块由团队网络方向同学主导，我负责其上的调度与业务层」。
